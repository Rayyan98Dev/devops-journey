## Models
- systemd is really a manager that starts, watches and restarts the programs that run the machine.
- A systemd unit is really a config file that describes something systemd manages, such as a program to run (`.service`) or a schedule (`.timer`).
  - **Check:** a unit isn't the program itself. The program is what the unit's `ExecStart=` line points to.
- The journal is really a diary that holds the output of every service on the computer.
  - **Check:** it also holds kernel messages. `journalctl` is the tool that reads it.

## PID 1
- PID 1 is the process ID of systemd. It's the first program the kernel starts.
- It matters because every other process is started by it, directly or indirectly. If PID 1 dies, the whole system goes down.
- Checked with `ps -p 1 -o pid,comm`, which showed `1 systemd`.

## Why use a manager
- A program started from a terminal dies when I close the terminal, because the terminal sends it `SIGHUP` ("hang up").
- It doesn't come back after a reboot, because nothing was set to start it at boot.
- What systemd does that starting a program myself doesn't:
  - waits for things it depends on before starting a program (for example, the network)
  - starts it at boot
  - restarts it if it fails
  - keeps its logs in one place (the journal)
- My laptop had 43 services running (I guessed 35).

## Reading `systemctl status sshd`
| Line | Meaning |
|---|---|
| `Loaded: ... /usr/lib/systemd/system/sshd.service` | where the unit file lives |
| `disabled` | not started at boot |
| `preset: disabled` | the OS's recommendation for whether it should be enabled |
| `Drop-In: ...` | extra settings layered on top of the unit file |
| `Active: inactive (dead)` | not running right now |

- For a running service, `status` also shows the process ID, memory use, how long it's been up, and the last few log lines.
- `systemctl cat sshd` shows the unit file. The line that says which program to run is `ExecStart=`.

## start vs enable
- `start` starts a program now, at runtime.
- `enable` flags it to start at boot, but doesn't start it now.
- `enable --now` starts it now and flags it for boot as well.

| | Now | At boot |
|---|---|---|
| `start` / `stop` | yes | no |
| `enable` / `disable` | no | yes |
| `enable --now` / `disable --now` | yes | yes |

- Link to firewalls: `start` is like runtime, and `enable` is like `--permanent`.
  - **Check:** unlike firewalld, there's no reload step. `start` and `enable` are two independent switches.

## journalctl
- `-u` = unit (for example, `-u NetworkManager` shows only its logs)
- `-b` = this boot only
- `-p err` = errors and worse
- `-n 20` = the last 20 lines
- `--no-pager` = print straight to the terminal

## Reading log "errors"
- My errors weren't critical: some didn't apply to a laptop, and the rest were safe to ignore.
  - `TDX not supported`: a security feature for cloud servers, not laptops.
  - `SMBus is busy`: a common, harmless kernel message on laptops.
  - `duplicate name 'org.freedesktop.Notifications'`: two notification programs are installed (KDE's and `dunst`), and the system ignores one.
- Lesson: read each line and decide whether it matters. The word "error" alone doesn't mean a problem.

## Parking-lot answer: `ssh` in the `public` zone

## Part 2: hands-on (Fri 16 Oct, moved because of the power outage)

### Biggest takeaways
- `enable` is really adding a shortcut (symlink) to the `default.target.wants` folder, and `disable` is removing it.
  - For my user service the folder is `~/.config/systemd/user/default.target.wants/`. The `WantedBy=default.target` line in `[Install]` is what decides which folder.
  - `ls -l` showed `lrwxrwxrwx ... heartbeat.service -> .../heartbeat.service`: the `l` means symlink and `->` shows where it points. After `disable` the folder was gone, because it was empty.
- Services running under systemd are restarted after a failure, and they get a different PID because they're not hard-coded into the config.
  - **Check:** a PID can't be hard-coded at all. The kernel gives every new process the next free number, and a restart is a brand-new process (66945 became 70957).
- `kill -9` counts as a failure, and `systemctl --user stop` is what actually stops a service (no restart).
  - **Check:** the signal I used was `SIGKILL` (`kill -9`), not `SIGHUP`. With `Restart=on-failure`, the "polite" signals (`SIGHUP`, `SIGINT`, `SIGTERM`, `SIGPIPE`) count as a clean exit, so no restart.

### What I built
- `~/devops-journey/scripts/heartbeat.sh`: prints `heartbeat: <time>` every 10 seconds. Needs `chmod +x` because `ExecStart=` runs it directly.
- `~/.config/systemd/user/heartbeat.service`:

```
[Unit]
Description=Heartbeat demo service

[Service]
ExecStart=%h/devops-journey/scripts/heartbeat.sh
Restart=on-failure

[Install]
WantedBy=default.target
```

- `%h` means my home folder.
- A user service (`systemctl --user`) runs as me, needs no `sudo`, and can't break the system.

### Commands
- `systemctl --user daemon-reload` re-reads unit files after adding or changing one.
  - Look-alike: firewalld's `--reload` loads saved firewall rules. Different job, similar name.
- `systemctl --user start | stop | status | enable | disable heartbeat`
- `journalctl --user -u heartbeat -n 5 --no-pager`
- `kill -9 "$(systemctl --user show -p MainPID --value heartbeat)"`: `$( )` drops the current main PID straight into `kill`.

### What the output showed
| Output | Meaning |
|---|---|
| `Active: active (running)` | my prediction was right |
| `CGroup:` with `bash` and `sleep 10` | the process family tree: my script and its child |
| `Main process exited, code=killed, status=9/KILL` | my `kill -9` |
| `Failed with result 'signal'` | systemd counted it as a failure |
| `Scheduled restart job, restart counter is at 1` | `Restart=on-failure` restarted it |
| `Stopping...`, `Stopped`, `inactive (dead)` | a deliberate stop, so no restart |

### Heredoc lesson (bug)
- Symptom: `cat > file <<'EOF'` never finished, and the terminal kept showing `>`.
- Cause: the lines were indented, so the closing line was `   EOF`. A heredoc only ends at a line that is exactly `EOF`.
- Fix: keep the closing `EOF` at the very start of the line (`Ctrl+C` escapes). The quotes in `'EOF'` stop `$(...)` from running while writing the file.
